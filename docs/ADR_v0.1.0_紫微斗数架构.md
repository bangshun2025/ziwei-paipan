## 二、上下文与约束

### 2.1 现状
- 产品为紫微斗数排盘软件 v0.1.0（PRD 已定稿），目标：纯本地单文件网页 + Clacky 侧栏扩展 + GitHub Pages 发布。
- 团队内有成熟参照系：八字排盘项目（`bazi-paipan`，v0.25.0+）——多文件 IIFE + 命名空间、`?test=1` 内嵌 247 条断言、SYSTEM.md/ALGORITHM.md/ADR 归档体系、三版发布流程。
- 运行目录已初始化（2026-09-02 Phase 0）：骨架 + 真相源三件套 + 模板 + 本文档归档；业务代码待实现。
- 参考实现已核：SylarLong/iztro（开源、社区活跃、含排盘断言测试）——提供安星规则背书与锚点数据来源。

### 2.2 约束
1. 纯本地零后端：无构建、无外部 API 依赖（发布后经 GitHub Pages 静态托管）。
2. 单文件产物可交付（借鉴八字 standalone 双形态：多文件开发态 + 单文件发布态）。
3. 正确性硬指标：出生日期 1800-2200 全区间可用；安星结果与权威实现/权威案例一致。
4. 口径争议（四化、流派、晚子时、闰月、年界）不得阻塞 v1：默认值落定 + 可配置 + 待裁决清单。
5. 文件产出铁律：开发期架构师产出均在架构师工作目录；归档阶段统一移入运行目录。

### 2.3 关键观察
1. **紫微与八字本质差异**：紫微以**农历生日**安星（非节气月），盘面为**十二宫位式**（非四柱表格式），存在流派（全书派/中州派/飞星）与争议口径（晚子时/闰月/四化/年界）。
2. **iztro 是高质量参考**：安星函数带口诀注释、有 1300+ 行排盘断言测试（如 2000-8-16 寅时女：命宫午、身宫戌、木三局、命主破军、身主文昌、大限庚辰…），可直接作为锚点来源。**但不可照抄代码**（TS/多依赖/配置体系复杂），只作口径背书。
3. **历法可复用八字经验**：八字项目已解决公农历转换、节气、真太阳时、1800-2200 数据覆盖；紫微安星正确性 70% 依赖历法正确，20% 依赖安星口诀，10% 依赖口径选择。
4. **宫位方向易错**：参考实现采用「宫位 index（寅=0，地支顺）+ 宫名按命宫起点循环」表示，迁移=对宫（±6）、命财官三合（±4/±8）自洽。手写实现必须用测试锚点锁死，勿凭绘图直觉。
5. **多文件同步事故前科**：八字 v0.20.2/0.20.3 因三文件不同步出事故，靠 `check-release.sh` + pre-commit 防线解决——本项目从一开始就采用「开发态多文件、发布态单文件」并内置一致性校验。

## 三、架构决策记录

### ADR-001：多文件模块化起步，零构建 IIFE + 命名空间

**决策**：采用与八字拆分后一致的形态：
```
index.html            → 页面壳（引入各 js，?test=1 注入测试）
js/constants.js       → CONST：历法表/星曜表/宫名表/四化表等静态数据
js/algorithm.js       → ALGO：安星纯函数（命身宫/五行局/紫微/主星/辅星/四化/大限）
js/render.js          → RENDER：盘面渲染（十二宫方盘/中宫/大限时间轴），纯展示
js/main.js            → APP：输入交互、事件绑定、初始化、?test=1 自检断言
```
全部 IIFE + window 命名空间挂载，零构建；`<script>` 按依赖顺序加载。

**理由**：
- v1 复杂度（历法 + 安星 20+ 张表 + 渲染 + 输入）超过单文件舒适区，多文件利于分工（测试师可按文件断言、实现者可并行）。
- 零构建是八字验证过的成熟路线，浏览器直接可跑，侧栏扩展 iframe 直用。
- 单文件产物仅在发布期合并（发布脚本执行），避免开发期多副本漂移。

**备选方案及否决原因**：
- 方案A：单文件起步（如八字 v0.16 前）—— 否决：v1 功能面已大于八字早期，后期拆文件有重构成本与回归风险。
- 方案B：Vite/打包构建 —— 否决：引入 node 链与产物复杂度，违背「纯本地单文件可交付、零依赖」约束；侧栏扩展/Pages 部署都更繁琐。
- 方案C：直接照搬 iztro TS 源码 —— 否决：类型/依赖/i18n/插件体系过度设计，且照搬第三方库不利于口径自主立宪。

**影响范围**：全部实现文件；目录骨架见《归档建议.md》。

### ADR-002：历法与真太阳时复用八字经验，独立历法模块

**决策**：
- 历法能力（公农历互转、年干支/月干支/日干支、节气、闰月判断）内聚为一个模块（可并入 constants.js 或独立 `js/lunar.js`）。
- 数据/算法来源沿用八字验证过的路线（sxtwl 经验 + 自有表），覆盖 1800-2200；不接在线 API。
- 真太阳时：输入「出生地经度 + 本地钟表时间」→ 经度时差 + 均时差修正 → 真太阳时 → 定时辰。出生地可选，缺省按北京时间（东八区 120°E）并提示。

**理由**：八字项目已把 1800-2200 农历/节气/真太阳时链路跑通并大量测试；紫微只在其上换「取用规则」（农历月日、时辰、年界可配），无需重造历法轮子。成本最低、风险最小。

**备选方案及否决原因**：
- 自研全量农历表 —— 否决：工作量大且易错，八字已有可用资产。
- 运行时在线 API —— 否决：违背纯本地零依赖。

**影响范围**：历法模块、输入层；与八字实现保持同源可交叉验证。

### ADR-003：以《紫微斗数全书》主流通用口径立宪（default 派）

**决策**：v1 安星口径 = iztro 所称 `default`（以《紫微斗数全书》为基础、社区主流通用）：
- 十四主星/六吉六煞/禄存羊陀/命主身主/四化表等按 ALGORITHM.md 已核对表。
- 中州派差异（如命主取年支、个别安星口径）不在 v1 实现；架构上留 `algorithm` 配置位，未来可插。
- 详细规则与差异登记见 ALGORITHM.md §21 与《需用户拍板决策项清单》。

**理由**：主流通用口径用户认知度最高、与参考引擎（文墨天机默认、iztro default）对齐度最高，利于双轨验证；PRD Q3 亦倾向主流通用。

**备选方案及否决原因**：
- 中州派 —— 否决：与主流对照源差异大，验证成本高，v1 无必要；留作后续可配置。
- 飞星派 —— 否决：体系差异（四化飞入飞出）超出 v1 范围。

**影响范围**：ALGORITHM.md 全部安星表；测试锚点基准。

### ADR-004：争议参数默认值 + 配置开关

**决策**：
| 参数 | 默认值 | 备选 | 说明 |
|------|--------|------|------|
| 年界（年干支/生年干判定） | 正月初一 | 立春 | iztro 默认 normal；对生年四化/年系星有影响 |
| 晚子时（23:00-24:00） | 归次日（forward） | 归当日（current） | 默认按次日排（日+1，时柱按子时） |
| 闰月 | 十五分界（闰月日>15 按下月，≤15 按本月） | 整月按下月 / 不处理 | iztro fixLeap 语义 |
| 时辰未填 | 默认子时并在 UI 明示「时辰未知」 | 不允许排盘 | PRD F1 决策 |

**理由**：社区主流默认与 iztro 默认一致，可最大程度对齐参考引擎；同时全部做成配置/常量，待邦顺裁决后可一键切换（详见决策项清单 Q4/Q5/年界）。

**备选方案及否决原因**：无备选冲突——这是「默认值」决策而非「是否支持」决策，所有选项均以可配置形式保留。

**影响范围**：历法模块取干支、紫微星/日系星安放、四化归属宫。

### ADR-005：正确性验证 = `?test=1` 内嵌断言 + 权威引擎双轨锚点

**决策**：
- 沿用八字 `?test=1`：main.js 内嵌 IIFE 断言，页面直接跑回归，L1-L4 分层（常量表/历法/安星/端到端）。
- 双轨锚点：
  a. **iztro 快照锚点**：从 iztro 测试与运行结果提取若干「输入→整盘 JSON」锚点（首批：2000-8-16 寅时女、2000-8-16 子时男、1990-1-1、2000-2-29、闰月案例、晚子时案例等），要求本实现逐项一致。
  b. **权威引擎人工案例**：文墨天机（ziwei001.cn）等生成 5-10 张不同命例盘，人工比对主星/四化/大限落宫。
- 锚点清单的起草由测试师协同（Leader 协调），本 ADR 提供数据源与首批候选；ALGORITHM.md §22 记录规则出处便于回溯。

**理由**：安星正确性是本产品生命线；纯靠人工目测不可靠（八字 v0.22.0 教训：数据表改动需常规行为对比）。iztro 断言是现成权威基线，成本最低。

**备选方案及否决原因**：
- 仅手工比对方盘 —— 否决：覆盖不足，回归无保障。
- 引入第三方测试框架 —— 否决：违背零依赖；浏览器直跑内嵌断言已被八字验证。

**影响范围**：main.js 测试段、测试师 test.md、CI/发布脚本可挂回归。

### ADR-006：SYSTEM.md 唯一真相源 + 按版本归档（八字范式）

**决策**：运行目录按八字档案范式初始化：
```
运行/
  README.md  SYSTEM.md  ALGORITHM.md  ARCHITECTURE.md  CHANGELOG.md
  index.html  js/  css/  scripts/(check-release 等)
  docs/_TEMPLATE/  docs/按版本归档 PRD/ADR/TEST/QA/RELEASE/RETRO
```
归档阶段由 Leader 协调执行（详见《归档建议.md》）。

**理由**：八字项目验证：唯一真相源 + 算法宪法 + 版本归档是多人协作不漂移的根基（奇门 v0.3.0 口径漂移教训）。

**备选方案及否决原因**：无文档直接编码 —— 否决：多 Worker 协作必然失序。

**影响范围**：Leader 归档任务、测试师 QA 报告位置、发布师版本记录。

### ADR-007：core（安星）与 ui（渲染/交互）分离

**决策**：ALGO 层只做「输入参数 → 结构化排盘结果」纯函数；RENDER/APP 层负责展示与交互。ALGO 不读 DOM、不依赖 window 事件，输出为可 JSON 化的盘面对象（含宫位/星曜/四化/大限），便于断言与未来多端复用。

**理由**：测试只需 import ALGO；渲染层可独立演进；为 v2 档案/流年/多主题预留空间。

**备选方案及否决原因**：计算与渲染混杂 —— 否决：无法做纯函数级断言，回归成本高。

**影响范围**：js/algorithm.js 与 js/render.js 边界；测试师可按层写用例。

### ADR-008：v1 功能边界锁定（大限入 v1，流年/小限/档案 v2）

**决策**：v1 交付 = PRD §功能模块 F1-F5 全量，其中「大限时间轴」入 v1（含起始岁=五行局数、每宫十年、阳男阴女顺/阴男阳女逆）；流年、小限、档案、十二长生/博士十二神等 v2。
- 大限展示：中宫或盘缘时间轴列出 12 大限「岁数区间 + 宫干支」，当前大限高亮（按虚岁定位，v1 可简化按当前年份）。

**理由**：PRD 明确定界；大限是命盘核心阅读元素，成本可控；避免 v1 被流年/小限拖累。

**备选方案及否决原因**：大限整体后置 —— 否决：PRD F5 已要求；大限算法与主星安放同源，先做边际成本低。

**影响范围**：ALGORITHM.md §大限；render.js 时间轴。
